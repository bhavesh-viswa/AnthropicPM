# Value-Aware Spend Controls

A prototype for Anthropic Enterprise PM: fuses **Analytics** (spend + estimated
value) and **Usage settings** (spend limits + credit approvals) into one
surface, so every budget and credit decision is made next to the ROI it
bought — instead of a value-blind dollar cap in a separate tab.

Scoped to seat-based Enterprise plans with usage credits enabled.

## The problem this fixes

Today, Analytics shows spend and estimated value. Usage settings lets admins
cap spend and approve credit requests — but that surface is entirely
value-blind: dollar-only limits, a binary block, and no idea what the last
dollar produced when a member asks for more budget. As autonomous agents
consume a growing share of credit spend with no human in the loop to vouch
for it, Finance and IT keep approving token budgets for value they can't see.

## Run it

```bash
npm install
npm run dev       # http://localhost:5173
npm run build && npm run preview   # production build check
npm run sanity     # prints the seeded dataset's key numbers to the console
```

No backend, no environment variables, no auth — everything is static,
seeded, client-side data. `npm run sanity` is a standalone script
(`scripts/sanity-check.ts`) that re-derives the headline numbers independently
of `lib/metrics.ts`, as a cross-check that the seed and the metrics library
agree.

## The three tabs

- **See** — spend & value by group and user: total net spend, **% spend
  verified** (the north star — spend tied to a shipped, lasting PR), %
  autonomous spend, a cost-per-lasting-outcome chart by group, and a
  searchable per-user table.
- **Set** — the group & user spend-limits table. Each row shows the limit
  next to the ROI it bought this month and a suggested limit derived from
  cost-per-outcome, plus the effective-limit resolver's logic spelled out
  inline (individual > group > org default, with a live toggle for how
  multi-group membership resolves).
- **Verify** — the credit-request queue. Every pending request shows the
  requester's realized ROI (cost-per-lasting-outcome, revert rate) next to
  the ask, an **auto-approve if ROI is top-decile** toggle, and — for a
  flagged high-revert autonomous agent — a **throttle this user** action with
  a projected spend-saved-vs-outcomes-protected estimate.

## Data model

Mirrors the real Analytics spend export plus the Usage settings surface:

- `spend_rows` — user_email, account_uuid, product (Chat / Claude Code /
  Cowork / Office Agents), model, model_family, request/token counts, net &
  gross spend, date, is_autonomous, repo.
- `github_outcomes` — pr_id, author_email, repo, created_at, state
  (merged / reverted / open), lasted_30d, lines_changed.
- `groups` / `group_members` — 3 SCIM groups, one user in two groups.
- `spend_limits` (scope: org / group / user) + `settings.multi_group_resolution`
  (higher / lower).
- `credit_requests` — user_email, requested_at, current_seat, mtd_spend_usd,
  status.

Two deliberate additions beyond the literal spec: `credit_requests[].request_id`
(a synthetic primary key, needed to target Approve/Deny mutations) and
`SeedData.asOfDate` (a synthetic "today" the whole demo is anchored to, so
MTD figures don't drift with wall-clock time).

### Simplifying assumptions

- **Fixed 2-month window**: Jun 1 – Jul 31, 2026. `asOfDate` = Jul 31, so "MTD"
  is always the full month of July — a clean 31-day window rather than a thin
  slice that would make percentages sensitive to which day is "today."
- **Flat 10% gross→net discount** on every spend row.
- **One `account_uuid` per user.**
- The join between spend and outcomes is faked by `user_email + repo + date`
  matching `author_email + repo + created_at`, standing in for the real
  system's missing direct foreign key.
- The dataset is generated by a seeded PRNG (`mulberry32`, fixed integer
  seed) — every `npm run dev` / `npm run build` produces byte-identical
  numbers, which matters because this README quotes them verbatim.
- Two numbers are load-bearing for the demo narrative and are constructed
  exactly rather than left to chance: **Payments' July spend is exactly 80%
  of its $3,000 group limit**, and **Felix's PR revert rate is exactly
  55.0%** (reverted / (merged + reverted), built from a fixed 22-reverted /
  18-merged bag rather than independent coin flips). Everything else in the
  dataset (day-to-day variance, other users' outcomes, token counts) is
  randomized around per-archetype parameters.

### Metrics (`src/lib/metrics.ts`)

- `cost_per_lasting_outcome` = Code-product net spend in scope ÷ count of PRs
  that were merged **and** still standing 30 days later.
- `pct_autonomous_spend` = autonomous net spend ÷ total net spend.
- `revert_rate` = reverted ÷ (merged + reverted); open PRs are excluded from
  the denominator since they haven't had a chance to revert yet.
- `pct_spend_verified` (**north star**) = spend tied to a lasting outcome ÷
  total spend, any product.
- `effective_spend_limit` resolves individual → group (via
  `multi_group_resolution`) → org default, and returns a human-readable
  explanation that's rendered directly in the Set tab, not just computed
  silently.
- `suggested_limit` = cost-per-lasting-outcome × current lasting-outcome
  count × 1.15 headroom — what it costs to sustain this month's output going
  forward, not a reward for good behavior.

## The seeded scenario

8 users across 3 SCIM groups:

| Group | Members | Story |
|---|---|---|
| **Payments** | Alice, Bob, Carol (+ Gabe) | High-ROI — cheap, mostly-lasting PRs |
| **Growth** | Dave, Erin, Felix | Felix is an autonomous agent with a 55% revert rate |
| **Platform** | Gabe (+), Hana | Baseline |

Gabe is in both Payments and Platform — the live worked example for the
multi-group resolver. Alice has an individual $1,200 limit that beats
Payments' $3,000 group limit regardless of that setting.

## 60-second demo script

1. **See** — land on the north-star card, **% Spend Verified**. Filter to
   Payments: its cost-per-lasting-outcome bar (~$61) is clearly the cheapest
   of the three, tagged "Best ROI." Growth is the most expensive (~$282,
   "Needs attention") — Felix's row in the user table shows a 55.0% revert
   rate at a glance.
2. **Set** — Payments is sitting at **exactly 80% of its $3,000 budget**,
   with a suggested limit that reflects its strong cost-per-outcome. Toggle
   "Lower limit wins" and watch Gabe's resolved limit flip live from
   Payments' $3,000 to Platform's $1,500 — the resolver logic is explicit,
   not hidden.
3. **Verify** — Carol's pending credit request sits right next to her
   realized ROI (~$47/outcome, 53% spend verified) and a "Top decile ROI"
   badge. Flip **Auto-approve if ROI in top decile** — her request is
   approved instantly with a toast explaining why. Felix's request, by
   contrast, is flagged as a high-revert autonomous agent and correctly
   never auto-approves.
4. **Throttle** — on Felix's card, click **Throttle agent**. The dialog
   shows the projected impact: throttling 70% of his autonomous usage saves
   roughly $1,700 over the 2-month window while risking only ~4 lasting PRs,
   because just ~13% of his autonomous-tied PRs ever lasted 30 days. Apply
   it — a "Throttled" badge follows him to the See tab, and the rest of
   Growth (Dave, Erin) is untouched.

**The point**: Payments is 80% through budget but every dollar maps to a
shipped, lasting PR — auto-approve its credit request. Growth's autonomous
agent is burning credits at a 55% revert rate — throttle that agent, not the
team. Both decisions made on one screen, next to the ROI, instead of a blind
yes/no in a separate settings tab.

## Stack

Vite + React + TypeScript + Tailwind v4 + hand-rolled shadcn/ui-style
components (Radix primitives) + Recharts. Fully client-side; state is a
`useReducer` overlay patched on top of immutable seed data (limit edits,
approvals, throttle actions, toggles), optionally persisted to
`localStorage` so a live demo survives a refresh. Use **Reset demo** in the
banner to clear it.
